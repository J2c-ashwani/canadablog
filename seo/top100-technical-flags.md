# Top 100 Technical Flags (static repo inspection)

This file was generated by a static code inspection of the repository (no live site crawl).
It highlights flags to confirm with a live crawl and recommends actions. Use this as a pre‑crawl checklist.

## Summary of repository findings

- app/layout.tsx includes site-level JSON‑LD (Organization + WebSite SearchAction) but no per-article BlogPosting/FAQ/Breadcrumb JSON‑LD. This reduces rich result eligibility for content pages.
- GlobalWikipediaLinker is mounted client-side in layout.tsx. The internal autolinking logic appears to inject links after hydration — this weakens server-side internal link visibility to crawlers.
- app/sitemap.ts programmatically builds a large sitemap including programmatic /grants/ pages and relies on two local files: `scripts/indexing-history.json` and `scripts/seo-recommendations.json` to compute indexed/click counts. If those files are missing or stale, the telemetry will misreport indexed/clicked counts.
- next.config.mjs sets X-Robots-Tag `noindex` headers for thank-you, admin, booking, partners/checkout and other routes — these are appropriate. No global noindex detected in repo-level config.
- Sitemap generation filters out some routes (e.g., blog archives, superseded slugs). The PSEO generator functions map many programmatic grant pages — confirm deduplication and canonical strategy for PSEO pages.
- Some redirects consolidate old slugs → new slugs. Good, but ensure canonical tags on destination pages point to the correct canonical (consistent trailing slash policy).
- layout.tsx has a fallback GA_MEASUREMENT_ID default string. Confirm that production env sets NEXT_PUBLIC_GA_MEASUREMENT_ID to your real GA4 property; otherwise analytics may be misattributed.

## Recommended live-crawl checks (Top100 pages)

For each top URL run these checks (I recommend using Screaming Frog, Sitebulb, or a lightweight Node script + curl):

1. HTTP status (200/301/404/5xx)
2. Response headers: check for `X-Robots-Tag` and `Content-Security-Policy` collisions
3. view-source HTML: ensure <link rel="canonical"> exists and points to the expected canonical (no unexpected canonical pointing to another host)
4. meta robots: check for `<meta name="robots" content="noindex">` or `noindex, nofollow`
5. Structured data presence: look for BlogPosting/Article, BreadcrumbList, FAQ on content pages
6. Internal links: ensure important hub pages link to these Top100 pages server-side (not injected by JS)
7. Rendered vs initial HTML: verify key internal links and JSON‑LD appear in initial HTML (curl + prerendered view)
8. Sitemap inclusion: confirm page appears in /sitemap.xml and in the sitemap entries created by the app (routes generated by app/sitemap.ts)
9. Mobile vs Desktop differences: check if mobile meta tags or AMP variants differ
10. Canonical conflicts: check server response for rel=canonical mismatches and redirect chains

Example curl command for one URL (raw HTML + headers):

curl -I -L 'https://www.fsidigital.ca/canada/small-business-grants'
curl -s 'https://www.fsidigital.ca/canada/small-business-grants' | sed -n '1,120p'

## Quick technical issues I discovered in-code (actionable)

1. Client-side internal linking: move GlobalWikipediaLinker autolinks into server-side content generation (during build/SSG) for programmatic pages to improve crawler visibility.
2. Per-page structured data: implement server-side BlogPosting/Article and Breadcrumb JSON‑LD in blog and guide templates; add FAQPage where appropriate.
3. Sitemap telemetry: do not rely on `scripts/indexing-history.json` for canonical indexed counts; instead pull real GSC/sitemap index statuses and store them centrally.
4. Canonical policy: ensure all programmatic pages add explicit `<link rel="canonical">` pointing to canonicalised URL (consistent trailing slash) and avoid multiple URLs differing only by punctuation/format.
5. Analytics env: ensure NEXT_PUBLIC_GA_MEASUREMENT_ID is set in production; remove or change fallback default placeholder to avoid confusion.
